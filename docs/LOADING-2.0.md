# 2.0 流式加载架构

本文说明 2.0 的照片墙加载方式。它参考了开源相册 Lap（`julyx10/lap`）的做法：
**先知道有多少、再按可视区分块取、缩略图按优先级排队**，而不是"整树扫完 → 一次性返回全部 → 才开始画"。

## 1. 1.11 与 2.0 的差别

```text
1.11：GET /api/photos
        └─ 服务端：整树 walk → 每个文件算 EXIF/尺寸（并发 8）→ 排序 → 全量 JSON
        └─ 前端：拿到全部条目后才渲染前 3 天，滚动再追加 3 天
      首屏 = 必须等整轮扫描结束（冷启动/刷新时最明显）

2.0 ：GET /api/library/summary          先拿总数 / 扫描进度 / 目录树
      GET /api/library/days             按天分组的元数据（表头 + 每天张数）
      GET /api/library/items?offset&limit  只取当前窗口那一段
      GET /api/library/neighbors/:id     查看器翻页的左右邻居
      GET /api/library/items-by-ids      按 id 取单条（?photo=<id> 直达时用）
      首屏 = 立刻铺占位格 → 可视块先出现 → 扫描继续跑，列表继续长
```

四个层次都是渐进式的：

| 层次 | 1.11 | 2.0 |
| --- | --- | --- |
| 数据 | 一次全量 JSON | 按 64~256 条一块，滚到哪取到哪 |
| DOM | 全量插入（前 3 天起步） | 只渲染可视区附近的块，上下用撑高的占位块维持滚动条 |
| 图片 | `loading="lazy"` 交给浏览器 | 调度器按"离视口中心近"排序，4 并发、每批 4 张，滚走的排队任务直接丢 |
| 扫描 | 扫完才有数据 | 走动目录时就占位（`total` 增长），解析完一项就填一格（`filled` 增长） |

## 2. 服务端

### 2.1 会话（`lib/media.js`）

一个照片文件夹只有一个**流式会话**，会话里保存：

```js
{
  slots,        // 格子数组：null = 还没解析完，item = 已就绪
  total,        // 格子数（= 已发现的媒体文件数，扫描期持续增长）
  filled,       // 已填充的格子数
  phase,        // idle | scanning | ready | canceled | error
  revision,     // 内容/顺序版本号：变化意味着格子索引不再对得上
  view,         // 完成后：按拍摄时间排序的视图（items / days / indexById）
  views,        // 按文件夹过滤的视图，惰性建立并缓存
}
```

扫描流程（`runStreamingScan`）：

1. `discover()` 递归走目录。**每发现一个媒体文件就 `slots.push(null)`**，
   同时顺手收集目录签名（`相对路径|mtimeMs`），所以扫描结束后不用再整树走一遍。
2. 8 个 worker 从共享队列取任务，`buildItem()` 解析完一项就写回对应格子并 `filled++`。
3. 全部完成后按拍摄时间排序、建目录树、预计算 `days`，`revision++`，写索引。

取消（`POST /api/scan/cancel`）会让 worker 下一次检查时抛 `SCAN_CANCELED`，
**已经填好的格子保留下来**，`phase` 变成 `canceled`，前端仍可浏览已扫描到的部分。

### 2.2 接口

| 接口 | 说明 |
| --- | --- |
| `GET /api/library/summary?folder=&refresh=1` | 总数、已填充数、照片/视频数、阶段、revision、目录树（ready 时）。`refresh=1` 强制重扫（目录签名没变则直接复用索引） |
| `GET /api/library/days?folder=` | 每天一条：`{ key, count, itemStart, city }`，`itemStart` 可直接当 offset 用 |
| `GET /api/library/items?offset=&limit=&folder=` | 窗口数据。扫描期返回**发现顺序**的片段（未就绪处为 `null`，前端保留占位格）；ready 后返回**拍摄时间顺序** |
| `GET /api/library/neighbors/:id?folder=` | `{ index, total, previous, next }`，`previous/next` 是完整条目 |
| `GET /api/library/items-by-ids?ids=` | 按 id 取条目 |
| `GET /api/photos` | **保留**：仍然等整轮扫描后返回完整图库（地图页、旧调用方继续可用） |

缩略图/预览/视频/原文件（`/api/thumb/:id` 等）改用 `getItemById()`，
一次哈希查表，**不会因为打开一张图而等整轮扫描**。

### 2.3 HEIC 的色彩：ICC 必须跟着转换结果走

iPhone 的 HEIC 里带着**完整的 ICC 色彩配置**（`meta/iprp/ipco/colr`，`colour_type='prof'`，
实测是 536 字节的 Display P3），libheif 解出来的 RGB 就是**这个色彩空间的数值**。
而转换链是 `heic-convert`（libheif/WASM）+ `jpeg-js`，写出来的裸 JPEG **没有 ICC** ——
下游 sharp 和浏览器只能把这些数值当 sRGB，于是颜色偏。

修法（`lib/heic-color.js`，2026-10-25）：

```text
readHeifColor(buffer)      从容器里读出 colr（prof/rICC → 完整 ICC；nclx → 原色/传输/矩阵编号）
attachIccToJpeg(jpeg, icc) 按 APP2/ICC_PROFILE 把 ICC 插到 SOI 之后（>65519 字节自动切段）
                           纯字节拼接：不解码、不重编码，像素一个数都不动
```

worker（`lib/heic-worker.js`）在 `heicConvert()` 之后立刻补上 ICC，于是下游 sharp 拿到的是
"带 ICC 的 P3 输入"，它会按默认行为（不调用 `withMetadata`/`keepIccProfile` 时就是
"转成 sRGB 并去掉元数据"）**正确地转成 sRGB** —— 输出是普通 sRGB 数值、不带标签，
任何看图工具都不会再看错。如果哪天要保留原色彩空间，用 `keepIccProfile()` 即可
（"数值不动、只带标签"，测试里有对照）。

缓存版本跟着动了：预览 `preview-v1` → `preview-v2`（旧的不再被命中），
缩略图版本 `3` → `4`（`prepareThumbnailCache()` 会自动删旧的重建）。

顺手修掉的坑：`heic-pool` 原来直接把调用方的 `ArrayBuffer` transfer 给 worker，
会把调用方的 Buffer **detach**（"Cannot perform Construct on a detached ArrayBuffer"），
小文件还可能连累 Buffer 内存池。现在先 `new Uint8Array(buffer)` 复制一份再 transfer。

文件夹过滤（`folder=all|unclassified|year-YYYY|<monthKey>`）在服务端完成：
首次请求某个过滤条件时从主视图过滤一次并缓存（只存引用，不复制条目对象）。

## 3. 前端

`public/photo-stream.js` 是加载器，`public/app.js` 只负责卡片/表头长什么样、
查看器与侧栏怎么联动。

### 3.1 布局模型

渲染和定位的最小单位是**块**：

- 扫描期：每块 6 行占位格；
- 完成后：每块一天（表头 + 该天的行）。

块高度是**先预估、首帧后实测校准**的（`calibrate()`）：卡片实际高度决定行高，
表头实际高度（含 `margin-bottom`）决定日期块高度。校准后重建一次布局，
滚动条长度就和真实内容一致。

高度公式必须与 CSS 对齐，否则滚动会漂移：

```text
grid 自然高度 = 行数 × 行高 − 行间距      （最后一行没有行间距）
扫描块高度   = 行数 × 行高                 （块的 padding-bottom 补回行间距）
日期块高度   = 表头 + 行数 × 行高 − 行间距 + 天间距
```

渲染时只插入可视区上下各 3 行的块，其余用 `.stream-spacer` 撑高：

```html
<div class="stream-spacer" style="height: ..."></div>   <!-- 上方内容高度 -->
<div class="stream-window"> …可视块… </div>
<div class="stream-spacer" style="height: ..."></div>   <!-- 下方内容高度 -->
```

**块是复用的，不会整窗口重建。** 加载器用 `renderedBlocks`（块序号 → DOM）记录已渲染的块：

- 滚动导致窗口变化时，只删除离开窗口的块、插入新进入窗口的块，其余 DOM 原样保留；
- 数据后到时只把该块里的占位格**原地**换成卡片（`patchBlock`），不重建整块。

这一条直接决定了流畅度：整窗口重建会让所有图片重新解码重绘，肉眼看到的就是"疯狂闪烁"。

**列数必须显式写回每一个旧网格。** 列数是从画廊实测宽度算出来的（`computeMetrics`），
只在**建块那一刻**写进 `grid-template-columns` —— 而块是原地复用的，不会因为列数变化就重建。
所以宽度变过之后（改窗口大小、最大化、浏览器缩放、侧栏出现/消失），必须由 `applyGridColumns()`
把新列数写回**已经渲染出来的**每个 `.stream-grid`：
新建块（`renderBlock`）和原地打补丁（`patchBlock`）都调它，`grid.__columns` 记着当前值、只在变时才写。
漏了这一步的症状很好认：**格子停在旧列数上一直放大着**（比如一行 8 张变成一行 5 张大格子），
刷页才会恢复。（`test:dom` 的 `[7.5]` 专门盯这条：1200px → 7 列、900px → 屏幕上每一块都变 5 列、
再回来又是 7 列，且网格节点还是原来那些。）

宽度变化的侦测有两路：`window.resize`（窗口本身变了）和挂在 `.gallery` 上的 `ResizeObserver`
（窗口没变但画廊自己变宽了：侧栏出现/消失、页面滚动条、DevTools 停靠）。
`ResizeObserver` 只看**宽度**、阈值 1px：高度每铺一次块都在变，跟着跑会把画廊位置缓存一直作废。

另外两个和流畅度相关的约定：

- **只有宽度变化才重算布局**。页面滚动条出现/消失会让可用宽度变化几像素，若每次都重建布局并
  回滚滚动位置，滚动时就会来回跳；`html { overflow-y: scroll }` 让滚动条常驻，进一步消除抖动。
- **画廊位置缓存**。滚动时每帧读 `getBoundingClientRect()` 会强制重排（因为同一帧还要写占位块
  高度），所以画廊的文档位置缓存 1 秒，只在窗口尺寸/状态变化时失效。

### 3.2 数据分块

数据块大小固定为"一屏可视条目数"，并夹在 64~256 之间；块号 = `floor(offset / chunkSize)`。
固定块边界保证来回滚动不会反复请求同一段。请求返回后若 `revision` 已经变了就丢弃结果。

### 3.3 缩略图调度

- 只给"可视区 ±1 行"内的卡片排队，优先级 = 离视口中心的距离；
- 4 并发、每批 4 张（与 Lap 的 `thumbnailScheduler` 一致）；
- 每次重新渲染先清空未开始的排队任务，滚走的图片不会继续占带宽；
- 已经加载过的 id 记在 `thumbDone` 里，重渲染时直接赋值，命中浏览器缓存。

### 3.4 扫描期不做按日期分组（刻意的取舍）

试过"边扫边按日期分组"（已解析的照片立刻按拍摄时间分成一天一组），最终**去掉了**：
分段每轮都可能在长，前端就得跟着调整已经铺好的块 —— 块结构一动，里面的
`<img>` 就会被重建、缩略图重新解码，肉眼和体感上就是"加载有点发涩"。
即使把分段做成"只往后追加 + 对齐到行边界"，它仍然是每轮都要算、都要比对的一份额外状态。

所以扫描期走**最短路径**：`days` 一律为空，块就是固定大小的占位块
（`SCAN_ROWS_PER_BLOCK = 6` 行一块，边界只跟 `total` 有关），照片填到哪就显示到哪。

- 服务端：扫描期 `summary.partialDays = false`、`days = 0`，`/api/library/days` 返回空表；
  按天分组只在**扫描完成**后由 `buildDays()` 算一次（精确、按拍摄时间排序）。
- 客户端 `buildBlocks({ days: [], total })`：每块 6 行，`itemStart` 落在固定格子上，
  扫描推进时**已铺好的块不会移动、不会缩水**（`test:geometry` 第 8 节有断言守着）。
- 扫描完成后换视图：顺序从"发现顺序"变成"拍摄时间顺序"，这时才出现日期表头。
- 实测：3000 张冷扫描 **5448 / 5165 ms**（带扫描期分组时是 5568~6058 ms），
  1200 张端到端首张照片 **521~547 ms**、扫描完成 **2538~2571 ms**，
  扫描期客户端只发 6 次 summary / 1 次 days（完成后取精确分组）/ 3 次 items。
- 保留的"扫描期也看得见"的能力只有**侧栏年/月目录**（见 3.5）——
  它是整个图库的属性、每轮只算一棵小树，且不参与照片墙的块布局，所以不拖速度。

### 3.5 侧栏年/月目录：扫描期就出现，并且能直接点

年/月目录是**整个图库**的属性（跟当前过滤无关），所以它跟着 `summary` 一起回，
扫描期也一样 —— 只用"已经解析完的前缀"建树，边扫边长：

- 服务端 `getScanFolders()`：按 `(已解析数, 已发现数)` 缓存，一轮只建一次树；
  `foldersToken`（含"未分类"张数）保证内容没变时不重复传那张表。
- 扫描期按目录过滤也**已经能用**：`resolveView()` 在非 ready 阶段会筛"已解析前缀"
  （`getScanFilteredItems()`，同样按进度缓存）。只筛前缀是为了让过滤后的下标**只往后追加**，
  不会因为中间某一格后解析出来而导致前面所有照片挪位。
- 扫描期的过滤视图不做按天分组（用纯占位块），`filterSupported` 一律为 true。
- 实测（用户的真实相册，34442 个文件，冷扫描）：**533 ms 就看到"2017 年"**，
  45 秒时已解析 10820/34439、列出 6 个年份；扫描期点 `year-2017` 直接返回 `total=605`。
  改之前要等整轮扫描结束（这个库约 100 秒）才会出现时间目录。
- 客户端不再单独发一次 `/api/library/summary?folder=all` 去取目录（老服务端才走那条兜底路径）；
  目录请求失败会撤掉"已同步"标记并重试，不会一次失败就永远空着。

### 3.6 扫描期与完成后的切换

扫描完成时顺序会从"发现顺序"变成精确的"拍摄时间顺序"（按天分段从近似变为精确，
城市等表头信息也在这时补上）。加载器会：

1. 记录当前视口顶部那张照片的 id；
2. 清空格子与分块缓存，重新按天布局；
3. 用 `neighbors` 接口查出该照片在新顺序里的下标，把滚动位置对回去。

### 3.7 查看器

查看器只持有"当前这张 + 服务端给的左右邻居"。
`←/→` 时取邻居（一次请求），并预加载相邻的那张图；跨过已加载窗口也不会卡住。
`?photo=<id>` 直达时若该照片还没进入窗口，用 `items-by-ids` 单独取回。

**查看器里到底是源文件还是转换图**，由 `viewerImageUrl()` 一个函数说了算：

```text
原生格式（JPG/PNG/WebP/GIF/BMP/AVIF）→ /api/file/:id    源文件本体，字节一致，不写缓存
HEIC / HEIF                          → /api/file/:id    先试源文件（见下）；失败才退回 /api/preview/:id
其它（TIFF/RAW…）                    → /api/preview/:id  转换预览（最长边 2560、q90、4:4:4、按 EXIF 摆正）
```

**HEIC/HEIF 的"先试原图"**（2026-10-25 加，和视频那套同构但更简单 —— 不需要预判；
开关和视频共用顶栏那个 **“直出”**：关掉时这段整个不生效，直接走转换预览）：

```text
第一下    <img src="/api/file/:id">（源文件）
成功      → sessionStorage 记 'album-image-source-v1:HEIC' = '1'
            本会话后面所有 HEIC 都直接源文件；邻居预加载也跟着预热源文件；
            详情面板的"显示来源"写"源文件（未经转换）"
失败      → 立刻换成 /api/preview/:id（转一次），提示写明"这台机器显示不了 HEIC 原图"
            **不记负面结论**：一张坏图不该让整个会话放弃试原图，试错一次的代价只是一次本地请求
重置      → 关掉标签页（sessionStorage 清掉）下次重新试
```

为什么值得试：Chromium 自己不带 HEIF/HEVC 解码器，但 Windows 上装了
「HEIF 图像扩展 + HEVC 视频扩展」之后 `<img>` 能直接显示 HEIC 原图 ——
于是**真原图、零转换、零缓存**，而且色彩由浏览器按原图自带的配置做管理
（以前那条转换链 `heic-convert` + `jpeg-js` 写出来的是**没有 ICC 的裸 JPEG**，
iPhone 的 Display P3 被当成 sRGB，颜色是偏的）。

预加载邻居也走 `viewerImageUrl()`，规则：

```text
原生格式的邻居                → 预热 /api/file/:id（源文件），翻页命中缓存
HEIC/HEIF 且已证实能直出的邻居 → 预热 /api/file/:id（源文件，不产生任何转换）
其它（TIFF、还没证实的 HEIC）  → 不预热
```

为什么转换类不预热：预热就等于"翻页时顺手把邻居也转一遍"，白花 CPU、白占盘 ——
用户要的是"真正打开那一张的时候才转"。已经打开过的那些不受影响：
`/api/preview` 的响应带 `immutable` 缓存，翻回来照样秒开。

这里踩过的坑：`preloadNeighbors()` 以前无脑预加载 `item.previewUrl`，而 `previewUrl`
对**所有**图片都存在，于是翻页时每翻一张就给左右邻居各转一张 2560px 的 JPEG ——
而那两张**永远不会被显示**（原生格式显示的是源文件），白转、白占盘。
实测真实相册里 15 个预览文件全部反查回 PNG 源文件。
现在：原生格式预加载源文件（超过 8 MB 的跳过，省一次无效读盘），转换类完全不碰。

详情面板里的"显示来源"一行就是把这个判定直接告诉用户：优先说**这次实际显示的**是什么
（每张图显示完会往 `imageDisplaySources` 记一笔），没显示过才按"会给哪个地址"预测。

**视频（HEVC）走的是同一套思路：优先直出、失败再转。** 三层：

```text
预判   canPlayType('video/quicktime; codecs="hevc"') 只是"快速路径"：
       'probably'/'maybe' → 'yes'；空串 → 'unsure'（**不是**"解不了"）。
       结论按"编码 + 容器"存 sessionStorage，一个键一份，值 '1' / '?'；
       老版本写的 '0' 一律当 'unsure' 读。
       （注意：sessionStorage 在同一个标签页里**刷新后仍然保留**，关掉标签页才会清 ——
        文档里以前写的"刷新页面就重新问"是不准确的。）
记忆   会话内按编码（上面的 sessionStorage）；跨会话按文件记"直出失败过"
       （localStorage，最多 500 条）；关掉再打开"直出"开关会清掉失败记忆
       （同一个开关也管图片：清 HEIC"能直出"的会话结论）
隐藏   直出失败 / 超时（查看器 5 秒、悬停预览 2.5 秒）→ 在转圈提示后面静默换成
       /api/video/:id 重来，不露黑屏、不留两个 <video>；并把该文件记进失败记忆
```

关键一条：**预判只决定提示文案，不决定"试不试"**。除了明确不值得试的编码，一律先真播一次源文件，
以实际结果为准 —— 因为 `canPlayType` 在这里本来就不可靠：`video/quicktime` 不是 Chromium
声称支持的容器、裸 `hevc` 也不是标准的 `hvc1.*` 写法，它经常回空串。而空串的语义是
"我不保证"，不是"肯定播不了"（Chromium 实际播放靠内容嗅探，很多 .mov 其实能播）。

判定矩阵（`videoPlaybackPlan()`）：

| 编码 | 预判 | 结果 |
| --- | --- | --- |
| h264 / avc1 / vp8 / vp9 / av01 | 不问 | 直出源文件（服务端本来也不会转码），reason `native-codec` |
| hevc / hvc1 / hev1 / h265 | 问一次 | 说能解 → 直出（`probe-ok`）；**答不上来 → 也先直出一次**（`probe-unsure`），试不动才转码 |
| mpeg4 / prores / 编码未知 | 不问 | 直接转码，reason `unsupported-codec`（不值得试） |
| 这个文件以前直出失败过 | — | 直接转码，reason `remembered` |
| 关掉"直出"开关（图片 + 视频一起管） | — | 图片一律转换、视频一律转码，reason `setting`（回到老行为） |

实况照片的伴随 MOV 复用同一套（`liveVideoPlan()`，把伴随项包装成视频条目；
服务端为此在实况照片条目上多给一个 `liveVideoCodec`），悬停预览和全屏"实况"播放
都是"能直出就直出、失败静默换转码"。

**踩到的坑（值得记一下）**：卡片元素是**扫描期**创建的，那时候实况照片的伴随视频信息
（id / 时长 / 编码）还没补上；扫描完成后条目虽然重新取过了，但**已渲染的卡片和元素池里的节点
都被复用**，闭包里还是旧条目 —— 于是"明明能直出还是去转码"。
现在卡片上记一个渲染指纹（`itemRenderKey()`：id / 类型 / 实况字段 / 时长），
`patchBlock()` 和 `nodeForIndex()` 都比对指纹，不一致就把那一格重建一次
（只重建变了的格子，不是整窗口重建）。这条同时修掉了"条目关键信息变了但卡片还是旧的"这类问题。

服务端**没有为此改动**：`fileUrl` 就是源文件，`videoUrl` 是需要时会转码的那一份，
前端在这两个地址之间做选择；`transcodeVideo()` 和 `cache\videos\` 那条路完全没变。

**点卡片去哪，由顶栏的"相册 / 系统"决定**（`handleCardOpen()`）：

```text
相册（默认）→ 一律进应用内查看器：图片显示源文件/转换预览，视频走上面的直出/转码链
系统        → 一律交出去：图片 → /api/open（系统照片），视频 → /api/open（PotPlayer 优先）
```

以前的坑：`handleCardOpen()` 里对视频是**硬编码**"直接 `/api/open`"，于是相册模式点视频
也会弹 PotPlayer。全屏查看器右下角的"原图"按钮不受这个开关影响 —— 它按定义就是"交给系统"。

### 3.8 实况照片（Apple Live Photo）的配对与展示

实况照片在磁盘上是两个文件：`IMG_5832.HEIC` + `IMG_5832.MOV`。2.0 把它们合成**一个格子**，
伴随的 MOV 不进格子（对应 Lap 的 `live_photo_video_id` / `media_subtype='live_photo'`）。

配对是在**目录列表阶段**定下来的（`planLivePhotoPairs()`，纯文件名运算、不读盘），
所以扫描期就能一次到位：图片一进格子就带 LIVE 角标，MOV 从头到尾不占格子 ——
用户看不到"MOV 先冒出来、扫完又消失"的跳动，`total` 全程也只数格子。

```text
discover()（每个目录）
  ├─ planLivePhotoPairs(本目录文件名)   → imageCompanion / companionImage
  ├─ 图片：占一格，liveInfo = {companionVideoPath, companionVideoName}
  └─ 同名 MOV：不占格，liveInfo = {companionImagePath}（只在 byId 里，供 /api/video/:id）
buildItem()：图片写 livePhoto / liveVideoId / liveVideoUrl（id 由路径直接算，不用等 MOV 解析完）
收尾 linkLivePhotoCompanions()：标识符复核，把错配拆开（被拆的 MOV 重新放回格子）
```

判定规则：

1. 同目录同名（图片扩展名限 `heic/heif/hif/jpg/jpeg`，视频限 `mov`）；MOV 侧额外认
   `IMG_5832_HEVC.MOV` 这种加后缀的写法；同名多个 MOV 时优先"名字正好对上"的那个，
   多出来的仍然是普通视频（一个 MOV 只配一张照片）。
2. **Content Identifier 复核**：图片头部 XMP 里的 UUID 与 MOV 的
   `com.apple.quicktime.content.identifier` 比对 —— 两边都有标识却不一致就**不配对**。
   优先用 `ffmpeg -i` 输出的标识（扫描视频时本来就会跑一次，零额外开销）；
   拿不到时（比如没装 ffmpeg、或从老索引迁移）从 **MOV 尾部**读 256 KB 补齐
   （QuickTime 的 keys/ilst 写在文件末尾）。图片侧只读头部 256 KB，
   而且**只读候选对**（有同名 MOV 的图片），几万张的库不会为此多读整库。
3. 两边都没有标识时退回文件名判据（iPhone 编号一台设备内唯一，照片和视频不会撞号）。

展示：

- 卡片（`app.js` 的 `createImageCard`）：`is-live` + `.live-badge`；
  鼠标停住 350 ms 在卡片内叠一个静音 `<video>`（`pointerleave` 立即移除节点并清 `src`，
  不让它继续占解码器）。视频是绝对定位的，出现/消失不改变卡片尺寸，不影响流式布局。
- 查看器：底部"实况"按钮（快捷键 `L`），视频叠在静止图上层播放，`ended`/`error` 后移除；
  静止图一直留着当海报。
- 节点回收：`photo-stream` 把卡片放进元素池或换项目时会调用 `node.__teardown?.()`，
  保证悬停预览不会跟着节点被复用而残留。

索引：v4 起记录实况照片关系（伴随视频带 `livePhotoCompanion` 存进 `items`，
所以从索引打开时 `/api/video/:id` 依然可用）。**v3 及以前的老索引不用重扫**：
读进来时按文件名补一次配对（图片头部 + MOV 尾部各 256 KB），补完就地写回 v4；
年/月张数也按"格子里的项目"重算（老索引把 MOV 也算进去了）。

## 6. 已知限制

- **扫描期不做按日期分组**（刻意的取舍，见 3.4）：扫描期间是一个"发现顺序"的
  占位块列表，照片填到哪就显示到哪；日期表头只在**扫描完成**后出现。
  好处是扫描期没有任何"重算分段 / 重排已铺好的块"的开销。
- 扫描期的**年/月目录**仍然可用（边扫边长，几秒内出现，扫描期也能点）；
  未解析的那部分照片暂时不在树里，所以扫描期的张数会一路涨到扫描结束。
  扫描期的目录过滤只作用于"已解析前缀"，因此刚解析出来、还没并进前缀的那几张
  可能暂时不出现在过滤结果里（扫描完成后一定准确）。
- 扫描期的顺序是"发现顺序"，完成后会重排一次；加载器会尽量把滚动位置对回原处，
  但重排瞬间仍可能有一次轻微跳动。
- 地图页仍走 `/api/photos`（需要完整条目做聚合），所以打开地图会等整轮扫描；
  后续可以改成基于 `days`/`items` 的增量聚合。
- **实况照片**：判定主判据是"同目录同名 + Content Identifier 一致"。如果导出工具把
  图片或视频改名成不同名字（例如 `IMG_5832.HEIC` 配 `IMG_5832_1.MOV`），就认不出来，
  两个文件会各占一格；`audit:live` 可以查这种情况。
- 实况视频首播要过一次转码（约 0.7 秒 / 3 秒素材），期间卡片上仍是静止图，
  不会闪；转完缓存在 `cache\videos\`。
- 伴随 MOV 不参与年/月目录计数、不参与分组、也不出现在地图上（它属于那张照片）。
- 2.0 只跑 Node 服务 + 浏览器，没有桌面窗口外壳：相册页面是浏览器标签页，
  服务跑在一个控制台窗口里（关掉即停止）。
